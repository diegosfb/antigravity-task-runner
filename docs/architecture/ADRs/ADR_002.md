# ADR-002: Separate Deterministic Game Engine From UI And Timing

## Status
Accepted

## Context
The specification requires deterministic and testable gameplay behavior for movement, collision handling, line clearing, game-over detection, and restart behavior. The backlog also explicitly recommends separating pure game-state logic from rendering and input handling. The system must support automatic falling, soft drop, and next-piece progression without coupling browser timers to game rules.

## Decision Drivers
- Deterministic gameplay is a core non-functional requirement.
- Automated test coverage must validate rules without DOM dependence.
- The same gameplay behavior must be shared by keyboard and touch controls.
- Runtime failures should be isolated and recoverable through restart.

## Selection Criteria
- Purity and determinism of gameplay state transitions.
- Ease of unit testing without browser mocks.
- Clear separation between rules, orchestration, and rendering.
- Support for reproducible piece sequences in tests.

## Considered Options
### Option 1: Embed gameplay state in React component state and effects
- **Pros**: Fewer files, quick to prototype.
- **Cons**: Harder to test, timing and rendering become entangled, duplicated logic risk grows quickly.

### Option 2: Pure reducer-based domain engine plus thin controller layer
- **Pros**: Deterministic, testable, easy to reason about, compatible with multiple input surfaces.
- **Cons**: Requires deliberate action and state design up front.

### Option 3: Finite-state-machine library or external state framework
- **Pros**: Explicit state transitions and visualization.
- **Cons**: Added dependency and conceptual weight for a relatively small v1 scope.

## Decision
Implement gameplay as a pure domain engine driven by plain-object actions and a thin application and controller layer that handles timers and browser input.

## Rationale
A reducer-style domain engine gives the project the cleanest path to deterministic tests and low-risk feature delivery. The controller can own elapsed time and input bindings, while the engine remains a pure function of state and action. This also makes it practical to model invalid moves as unchanged state and to reproduce exact sessions using explicit seeds.

## Consequences

### Positive
- Core gameplay can be tested without DOM interaction.
- Keyboard and touch controls can share the same action contract.
- Game-over, restart, and line-clear logic live in one place.
- Regressions are easier to isolate and fix.

### Negative
- More upfront design work is required for state shape and actions.
- Developers must resist convenience shortcuts in UI code.

### Neutral
- The controller still needs careful timer handling, but timer bugs remain outside the domain rules.

### Risks
- Poorly designed actions could make the reducer harder to extend.
- Unseeded randomness would undermine determinism if introduced later.

## Implementation Notes
- Store rngSeed and bag queue in state.
- Model gravity via TICK actions with elapsed milliseconds.
- Model soft drop as explicit pressed state instead of a separate movement code path.
- Keep selectors separate from reducers.
