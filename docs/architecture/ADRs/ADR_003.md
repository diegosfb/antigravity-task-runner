# ADR-003: Use DOM Grid Rendering With Unified Keyboard And Touch Actions

## Status
Accepted

## Context
The UI only needs to render a bounded playfield, one next-piece preview, and a small set of visible controls. The spec requires responsive desktop and mobile behavior, keyboard support on desktop, and touch-accessible controls on mobile. The architecture must remain simple and easy for first-time players to understand.

## Decision Drivers
- Responsive layout and clear controls are mandatory.
- Rendering must stay easy to test in components and browsers.
- The same gameplay rules must apply to desktop and mobile inputs.
- v1 excludes advanced visual features that would justify a more complex renderer.

## Selection Criteria
- Simplicity of implementation.
- Ease of responsive design and accessibility.
- Low testing friction for board and control behavior.
- Adequate runtime performance for a 10x20 grid.

## Considered Options
### Option 1: HTML and CSS grid rendered through React components
- **Pros**: Simple, accessible, easy to inspect in tests, works naturally with Tailwind.
- **Cons**: Less optimized than canvas for extremely high-frequency rendering.

### Option 2: Canvas-based renderer
- **Pros**: Efficient drawing and full control over visuals.
- **Cons**: Harder to test and less natural for accessible controls and DOM-based assertions.

### Option 3: SVG renderer
- **Pros**: Declarative and scalable visuals.
- **Cons**: More markup complexity than needed for a simple block grid.

## Decision
Render the board and preview using DOM elements styled as a grid, and route both keyboard and touch controls through the same domain action layer.

## Rationale
A DOM grid is fully sufficient for the scale of this game and keeps the implementation readable, responsive, and test-friendly. The control strategy is more important than the rendering strategy: keyboard and touch must dispatch the same actions so gameplay behavior never diverges by platform.

## Consequences

### Positive
- Component tests can assert real rendered cells and control states.
- Tailwind can express layout and sizing without custom drawing code.
- Touch controls remain accessible and visible on mobile.
- Keyboard and touch parity is enforced by design.

### Negative
- Rendering efficiency is lower than canvas, though still acceptable for v1.
- Developers may be tempted to add decorative DOM complexity that hurts performance.

### Neutral
- The app can still migrate to canvas later if performance or art direction changes.

### Risks
- Re-rendering every cell unnecessarily could create jank on low-end devices.
- Touch event handling can become inconsistent if press and release behavior is not standardized.

## Implementation Notes
- Use memoized presentational components only where profiling shows value.
- Keep touch targets large and labeled.
- Prevent default browser scroll behavior for soft-drop touch controls when necessary.
- Render from selectors, not from ad hoc computed state inside components.
