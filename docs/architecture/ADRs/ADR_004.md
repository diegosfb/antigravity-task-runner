# ADR-004: Deploy As Static Assets On Vercel With CI Quality Gates

## Status
Accepted

## Context
The application is fully client-side in v1 and therefore has no runtime backend dependencies. The deployment model should be simple, fast, preview-friendly, and easy to roll back. The project already uses npm-based workflows, and the release process should enforce automated validation before production exposure.

## Decision Drivers
- Static delivery is sufficient for the product scope.
- Preview environments are useful for validating gameplay and responsive behavior.
- Release risk should be reduced through automated quality gates.
- Operational overhead should stay minimal.

## Selection Criteria
- Native support for static SPA hosting.
- Easy preview deployments per pull request.
- Low operational maintenance cost.
- Clean integration with CI checks.

## Considered Options
### Option 1: GitHub Pages
- **Pros**: Low cost, simple hosting for static files.
- **Cons**: Weaker preview deployment ergonomics and hosting configuration flexibility.

### Option 2: Vercel static deployment
- **Pros**: Excellent preview workflow, CDN delivery, simple SPA hosting, easy rollback.
- **Cons**: Adds platform dependency for deployment.

### Option 3: Custom object storage plus CDN
- **Pros**: Maximum hosting control.
- **Cons**: More infrastructure setup and maintenance than v1 warrants.

## Decision
Deploy the built SPA as static assets on Vercel and require CI quality gates before deployment promotion.

## Rationale
Vercel gives the project the simplest path to production-grade static hosting with preview deployments and rollback-friendly immutable assets. Since there is no backend, a more elaborate infrastructure footprint would be wasted effort. CI quality gates align with the need for deterministic game correctness and safe iteration.

## Consequences

### Positive
- Static hosting keeps runtime operations simple.
- Pull requests can be validated in realistic browser environments.
- Rollbacks are straightforward.
- CDN delivery supports good global performance.

### Negative
- Deployment becomes somewhat platform-coupled.
- Hosting configuration lives outside the application runtime and must still be maintained.

### Neutral
- The static deployment model remains compatible with a future backend added on a separate boundary if requirements change.

### Risks
- Teams may skip browser validation if CI only runs unit tests.
- Hosting headers could drift if not version-controlled alongside the app.

## Implementation Notes
- Enforce npm run lint, npm test, and npm run build before production deployment.
- Run Playwright on pull requests or before merge to main.
- Configure SPA fallback and strict security headers.
- Use immutable hashed assets and preserve build artifacts for traceability.
