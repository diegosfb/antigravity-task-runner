# ADR-001: Adopt a Client-Only React/Vite/Tailwind SPA

## Status
Accepted

## Context
The specification requires a browser-based single-player Tetris game that is fully client-side in v1 and explicitly excludes backend services, persistence across sessions, and multiplayer. The architecture guidance prefers JavaScript for the frontend and Tailwind CSS for styling. The solution needs to be simple to implement, easy to test, and straightforward to deploy.

## Decision Drivers
- Fully client-side runtime is mandatory for v1.
- Fast implementation and low operational complexity are priorities.
- Responsive layout and maintainable UI composition are required.
- Agents need a familiar, modular frontend stack with strong ecosystem support.

## Selection Criteria
- Zero backend requirement at runtime.
- Low build and deployment complexity.
- Strong support for reusable UI components and test tooling.
- Good ergonomics for a small bounded game UI.

## Considered Options
### Option 1: Vanilla JavaScript with minimal tooling
- **Pros**: Lowest dependency count, very small runtime, direct browser control.
- **Cons**: Less structure for multi-agent implementation, weaker component reuse, more manual UI state wiring.

### Option 2: React with Vite and Tailwind CSS
- **Pros**: Clear component model, fast local build and dev cycle, easy responsive UI composition, mature test ecosystem.
- **Cons**: Adds framework dependencies and some rendering overhead compared with vanilla JS.

### Option 3: Next.js application
- **Pros**: Strong React framework conventions, easy deployment, future server features available.
- **Cons**: More framework surface area than needed, server-oriented features are out of scope for v1.

## Decision
Use a client-only SPA built with JavaScript, React, Vite, and Tailwind CSS.

## Rationale
React + Vite + Tailwind provides the best balance of delivery speed, maintainability, and testability for a small browser game. It honors the JavaScript and Tailwind guidance while avoiding the extra framework complexity of a server-capable platform. The UI needs are modest but still benefit from structured components and a mature testing story.

## Consequences

### Positive
- Clean component boundaries for board, preview, controls, and status overlays.
- Fast local iteration and lightweight static deployment.
- Good compatibility with Vitest, Testing Library, and Playwright.
- Straightforward responsive styling using Tailwind.

### Negative
- Framework overhead is higher than a hand-written DOM implementation.
- Team discipline is required to keep gameplay rules out of React components.

### Neutral
- The runtime stays purely client-side, so future persistence or multiplayer would require additional architecture work.

### Risks
- UI code could accidentally absorb domain rules if boundaries are not enforced.
- Tailwind utility growth can become noisy without component discipline.

## Implementation Notes
- Scaffold with Vite in JavaScript mode.
- Use Tailwind for layout, spacing, sizing, and control states.
- Keep runtime as a static SPA with no serverless functions.
